# Introduction aux cas d'utilisation UML

## Objectif du document

Ce document présente la méthodologie utilisée pour décrire les cas d'utilisation de la marketplace.

Les cas d'utilisation permettent de représenter les interactions entre les acteurs du système et les fonctionnalités disponibles.

Ils répondent principalement à la question :

> Qui utilise le système et quelles actions peut-il réaliser ?

---

# Définition d'un cas d'utilisation

Un cas d'utilisation représente une fonctionnalité du système permettant à un acteur d'atteindre un objectif précis.

Un cas d'utilisation décrit :

- un acteur qui interagit avec le système ;
- un objectif recherché ;
- les actions possibles ;
- les règles associées.

Exemple :

Un acheteur souhaite acheter un produit.

Le cas d'utilisation associé est :

Acheter un produit

---

# Objectif des diagrammes de cas d'utilisation

Les diagrammes UML permettent de visualiser :

- les acteurs du système ;
- les fonctionnalités principales ;
- les relations entre acteurs et fonctionnalités.

Ils permettent de :

- faciliter la compréhension du projet ;
- valider les besoins fonctionnels ;
- servir de référence avant la conception technique ;
- éviter les incompréhensions pendant le développement.

---

# Périmètre des cas d'utilisation

Les cas d'utilisation concernent uniquement les aspects fonctionnels de la marketplace.

Ils décrivent :

- les actions des utilisateurs ;
- les services proposés par la plateforme ;
- les interactions entre les différents rôles.

Ils ne décrivent pas encore :

- le code source ;
- les classes Java ;
- les composants React ;
- les tables de base de données ;
- les détails techniques d'implémentation.

---

# Acteurs du système

La marketplace possède plusieurs acteurs principaux.

Chaque acteur correspond à un rôle pouvant être associé à un compte utilisateur.

## Acteurs principaux

| Acteur | Description |
| Acheteur | Utilisateur recherchant et achetant des produits |
| Vendeur | Utilisateur proposant et gérant des produits |
| Livreur | Acteur responsable de la livraison des commandes |
| Support | Acteur chargé de l'assistance utilisateur |
| Administrateur | Acteur supervisant l'ensemble de la plateforme |

---

# Organisation des cas d'utilisation

Les cas d'utilisation seront séparés par acteur afin de faciliter la maintenance de la documentation.

Organisation prévue :

04-cas-utilisation/

├── 04.2-cas-utilisation-acheteur.md
├── 04.3-cas-utilisation-vendeur.md
├── 04.4-cas-utilisation-livreur.md
├── 04.5-cas-utilisation-support.md
└── 04.6-cas-utilisation-administrateur.md

Chaque document présentera :

- l'acteur concerné ;
- ses objectifs ;
- ses cas d'utilisation ;
- les descriptions fonctionnelles associées.

---

# Convention de nommage des cas d'utilisation

Chaque cas d'utilisation possède un identifiant unique.

Format utilisé :

UC-[ACTEUR]-[NUMERO]

Exemples :

UC-A01

Correspond à :

Use Case Acheteur numéro 01

---

# Codes des acteurs

| Code  | Acteur            |
| A     | Acheteur          |
| V     | Vendeur           |
| L     | Livreur           |
| S     | Support           |
| AD    | Administrateur    |

---

# Exemple de notation

Exemple :

| Code      | Nom                           | Acteur    |
| UC-A01    | Créer un compte               | Acheteur  |
| UC-V01    | Ajouter un produit            | Vendeur   |
| UC-L01    | Mettre à jour une livraison   | Livreur   |

---

# Diagrammes UML

Les diagrammes seront réalisés avec PlantUML.

Les fichiers sources seront conservés au format :

.puml

Les diagrammes générés pourront être exportés sous forme d'image pour faciliter la consultation.

Structure prévue :

diagrammes/

├── diagramme-global-use-case.puml
├── diagramme-acheteur.puml
├── diagramme-vendeur.puml
├── diagramme-livreur.puml
├── diagramme-support.puml
└── diagramme-administrateur.puml

---

# Règle de conception

Les cas d'utilisation doivent être validés avant toute conception technique.

Ordre de travail :

1. Identifier les besoins fonctionnels.
2. Définir les acteurs.
3. Définir les cas d'utilisation.
4. Valider les interactions.
5. Générer les diagrammes UML.
6. Passer à la conception technique.
